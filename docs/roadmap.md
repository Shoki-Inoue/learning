# 学習ロードマップ

- 作成日: 2026-10-06
- 見直し: フェーズが一区切りしたとき、または興味・仕事が変わったとき

## 現状
- 実務: SES で TypeScript / React / AWS。自社サービスで TypeScript、Rust（試しレベル）
- 課題: 最近コードを書いておらず、良い実装・設計を判断できる自信がない。基礎を体系的にやってこなかった
- ペース: 不定期

## 目標
- 数年後: テックリード / シニアエンジニア / アーキテクト
- そのために必要な力: **「なぜこの実装・設計が良いのか」を根拠をもって判断し、説明できること**

## 進め方の原則
1. **同時に進めるのは1〜2テーマ + 本1冊まで**。分野が広いので、並行すると全部が中途半端になる
2. **どのテーマでも必ずコードを書く**。読むだけで終わらせない（「書いていない」状態を解消する）
3. **1回 = 小さな1歩**。30分で区切れる単位にして、「次にやること」を更新して終える
4. **判断を言葉にする**。「AとBのどちらにしたか・なぜか」を README.md に残す（テックリードの基本動作の練習）

## 2つの進め方を組み合わせる
- **読む（インプット）**: `books/` で本を章ごとに読み、自分の言葉でノートを書く
- **書く（アウトプット）**: `topics/` で実際にコードを書いて確かめる
- 本で「試したい」と思ったことは `topics/` のテーマに持っていく

## フェーズ

### フェーズ1: 良いコードの判断軸をつくる（TypeScript）
すぐ仕事に効き、いちばん大きな課題に直接取り組めるので最初にやる。慣れている TypeScript を使い、言語の学習ではなく設計に集中する。

**TypeScript の基礎を並行して進める。** 設計の判断は、言語の仕組みを正確に知っていないとできない。基礎で学んだことを設計のテーマで使う、という形で組み合わせる。

| テーマ案 | 内容 |
|---|---|
| `ts-fundamentals` | 型システム（構造的型付け、union と絞り込み、ジェネリクス、`unknown` と `any`）、非同期処理（イベントループ、Promise）、モジュール、`tsconfig` の strict 設定 |
| `design-refactoring-ts` | 読みにくいコードをテストで守りながらリファクタリングする |
| `design-principles-ts` | 凝集・結合、依存の向き、SOLID を小さなコードで確かめる |
| `test-unit-testing-ts` | 良いテスト・悪いテスト、テストしやすい設計 |
| `ts-type-design` | 型で不正な状態を表現できなくする設計 |

参考: 『プロを目指す人のためのTypeScript入門』、TypeScript 公式 Handbook、『リーダブルコード』、『良いコード/悪いコードで学ぶ設計入門』、『リファクタリング 第2版』（Martin Fowler）、『単体テストの考え方/使い方』（Vladimir Khorikov）

### フェーズ2: 基礎（コンピュータの仕組み）
フェーズ3の判断（性能、障害、スケール）の土台。普段使っている Web や AWS を、仕組みから理解する。

| テーマ案 | 内容 |
|---|---|
| `net-http-tcp` | HTTP / TCP / DNS / TLS。簡単な HTTP サーバーを自作する |
| `lowlevel-linux-process` | プロセス、メモリ、ファイル、I/O（WSL で実験） |
| `rust-ownership` | Rust でメモリ管理を体感する（自社サービスの Rust にも活きる） |
| `db-internals` | インデックス、トランザクション、分離レベル |

参考: 『Webを支える技術』、『［試して理解］Linuxのしくみ』、『プログラミング Rust』

### フェーズ3: アーキテクチャとシステム設計
アーキテクトを目指すための中心。フェーズ1・2の判断軸を、システム全体の規模に広げる。

| テーマ案 | 内容 |
|---|---|
| `arch-layered-clean` | レイヤード / クリーンアーキテクチャを小さなアプリで実装して比べる |
| `arch-ddd` | ドメイン駆動設計の考え方とモデリング |
| `arch-distributed-systems` | 複製、分割、一貫性、メッセージング |
| `infra-aws-cdk` | AWS の構成を CDK（TypeScript）でコード化する |
| `infra-observability` | ログ、メトリクス、トレースで障害を追えるようにする |

参考: 『ソフトウェアアーキテクチャの基礎』、『ドメイン駆動設計をはじめよう』、『データ指向アプリケーションデザイン』

### 全フェーズ共通: テックリードとしての練習
- 設計の判断を **ADR（Architecture Decision Record）** の形で書く練習をする
- 仕事で見かけたコードや設計の良し悪しを、学んだ観点で言語化してみる

## 最初の一歩
次の3つを並行して始める。
1. **読む**: 『ソフトウェアエンジニアリングの基礎』1章
2. **基礎**: `topics/ts-fundamentals/` で型システムから始める
3. **設計**: `topics/design-refactoring-ts/` で、テストがない読みにくいコードにテストを書き、リファクタリングする
